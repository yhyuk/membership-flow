## 1. 핵심 도메인 결정 — 회원 단일 상태 모델

### 결정

`subscriptions` 테이블을 `UNIQUE(member_id)`로 두어 **회원당 정확히 1개 상태**를 갖도록 했습니다.

### 배경

ASSIGNMENT는 "회원은 3가지 구독 상태 중 1개의 상태만 가질 수 있다"고 명시합니다. 동시에 "회원은 구독 및 해지를 여러 번 수행할 수 있다"고도 합니다. 이 둘은 모순이 아니라 **"한 회원 = 한 상태, 단 여러 번 변경 가능"**으로 양립합니다.

초기 구현은 `UNIQUE(member_id, channel_id)`로 두어 회원이 채널별로 독립된 상태를 갖는 구조였습니다. 이 경우 홈페이지로 가입한 회원을 콜센터로 해지하는 정상 시나리오가 "콜센터 채널엔 구독 기록 없음 → 거부"로 실패합니다. ASSIGNMENT 예시 응답("홈페이지 가입 → 모바일앱 프리미엄 → 콜센터 해지")과 정면으로 충돌하므로 **단일 상태 모델로 수정**했습니다.

### 트레이드오프

- 채널은 "상태 변경 창구"로만 의미가 축소됩니다. `subscriptions.channel_id`는 최종 변경 채널(추적용)이며, 채널별 흐름은 `subscription_history`에 남습니다.
- 만약 도메인이 "채널별 독립 구독"(예: 넷플릭스 가구 공유)이었다면 복합 키가 맞습니다. 본 과제 요구는 회원 단일 상태이므로 현재 모델이 정답입니다.

## 2. LLM 호출 캐싱 미적용

### 결정

동일 회원이 이력 조회를 N번 호출하면 Gemini도 N번 호출됩니다. **캐시를 본 과제에 구현하지 않고, 설계만 문서화**했습니다.

### 사유

- 과제 평가의 핵심은 도메인 정확성·장애 대응·인프라 설계이며, 캐시는 그와 직교하는 최적화입니다.
- 캐시를 잘못 적용하면(예: DEGRADED 응답까지 캐시) 오히려 버그를 만듭니다 — 정확히 설계하려면 키/TTL/실패 처리까지 따져야 하고, 이는 별도 작업 단위입니다.
- 단일 인스턴스 가정에선 LLM 호출 빈도가 낮아 실익이 작습니다.

### 적용 시 설계 (운영 전환 시)

- 캐시 키: `memberId + lastHistoryId` → **새 이력이 생기면 키가 바뀌어 자연 무효화** (수동 evict 불필요)
- 저장소: 단일 Task는 Caffeine in-memory, Fargate 다중 Task는 ElastiCache(Redis)
- TTL 30분 + **성공(NORMAL) 응답만 캐시** (DEGRADED 캐시 금지 → LLM 회복 시 자동 복원)

## 3. 테스트 전략의 한계

| 항목 | 현재 | 한계 / 보강 방향 |
|---|---|---|
| 단위·슬라이스 | H2 인메모리 | MySQL 방언 차이를 못 잡음 |
| 통합 | Testcontainers MySQL 8 (ASSIGNMENT 시나리오 4종) | 동시성(낙관락) 부하 테스트는 미포함 |
| 커버리지 측정 | 미도입 | JaCoCo 리포트 추가 시 정량 시그널 강화 가능 |
| 부하/성능 | 없음 | k6/Gatling 등으로 커넥션 풀·CB 임계 검증 가능 |

H2와 MySQL의 방언 차이(예: BIT(1), 시퀀스 전략) 위험은 Testcontainers 통합 테스트가 실제 MySQL 8 + Flyway로 보완합니다.

## 4. 인프라 — 의도적으로 미적용한 것

| 미적용 항목 | 사유 |
|---|---|
| Redis 캐시 | 이력 조회 빈도 낮음. RDS read replica로 대체 가능 (§2 캐싱 설계 참고) |
| Kafka / 이벤트 소싱 | 외부 이벤트 통합 요구 없음. `subscription_history` append-only로 도메인 이벤트 흔적 보존 |
| 마이크로서비스 분리 | 단일 도메인. 모놀리스가 통신/배포 복잡도에서 우월 |
| GraphQL | REST 2개 엔드포인트로 충분 |
| Multi-Region (DR) | RPO/RTO 목표가 일반 SLA 수준이라 cross-region 비용 대비 이득 미비 |
| AWS Lambda | 외부 API latency + cold start 결합 시 UX 저하. Fargate가 적합 |
| API Gateway | ALB로 충분. 비용/복잡도 대비 추가 가치 없음 |
| Step Functions | 트랜잭션이 2-Phase로 단순. 워크플로우 엔진 미요구 |

## 5. 알려진 미세 이슈

- **검증 우선순위 미묘함**: `current=NONE, target=NONE`은 "동일 상태(ALREADY_IN_TARGET_STATE)"와 "해지 불가(NO_ACTIVE_SUBSCRIPTION)" 둘 다 해당합니다. 사용자 의도가 "해지"임이 명확하므로 후자를 우선 노출하도록 분기 순서를 조정했습니다.
- **`DOWNGRADE_NOT_ALLOWED` / `INVALID_STATE_TRANSITION`은 방어용**: 현재 의도 추론 로직상 정상 흐름에서는 도달하지 않으나, 정책 변경 시 안전망으로 유지합니다.
- **HTTP 상태 다양성**: 400/404/409/422/500/502 6종입니다. 422를 400으로 합치는 축약도 가능하나, "요청 못 읽음(400)"과 "도메인 거부(422)"의 모니터링 분리 이점을 위해 유지했습니다.
